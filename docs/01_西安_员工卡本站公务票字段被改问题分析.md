# 西安员工卡本站公务票（文件1D定期票）字段被改问题分析报告

> 分析对象：reader-xian 仓库 3018-3030-TP（tp_ver = 0x2280714）
> 分析日期：2026-08-25
> 问题：生产环境员工卡本站公务票的 有效期（开始时间/时长/时长类型）、激活标志、有效区间 等字段被修改，卡片变为非法卡；本版本为"修复过的版本"但问题依旧。

---

## 0. 结论摘要

1. **全量审计结论**：CPU 卡文件 1D（本站公务票/员工票属于 FEETYPE_PERIOD 定期票）只有 **3 类写卡路径**：首次使用激活（正常）、**20260715 修复块（恶性修改源头）**、以及 5 处"恢复块"（本意是防修改，实际全部失效）。没有任何路径会写有效区间、也没有任何路径会清除激活标志。
2. **上次修改（20260715 块）有严重问题**：它把"改有效期"的代码放进了**读文件函数** `CPU_GetFiles1d` 里，任何进站/出站/补票/查询操作只要满足一个依赖**站级 PC 时钟**的条件，就会把卡的时长强制改成 24 个月、开始时间改成读卡器当前时间并写回卡内。原始时长被永久丢弃。
3. **生产根因**：修复块的触发条件 `已激活 && 读卡器时钟 < 卡内有效期开始日期` 用不可信的站级时钟做判断——只要某台机器的时钟比卡激活日期慢一天（时钟回拨、未对时、BIOS 掉电等），它就会**无差别改坏所有已激活定期票**；改坏后的卡时长与票种定义不符，后台判为非法。而"修复"本身没有升级版本号（tp_ver 仍是 0x2280714），现场无法区分新旧固件，问题持续。

---

## 1. 背景与代码定位

- 员工卡本站公务票是 CPU 卡的**定期票（XA_FEETYPE_PERIOD）**，数据在文件 1D（16 字节，APDU `00 B0 9D 00 10`），解析用 `xaFile1C` 联合体的 `_File1C` 位域结构（`xa_cpu20_operation.h:236-281`）。
- 进站 `xa_CPU_entry`（`xa_cpu20_operation.c:1402-1432`）、出站 `xa_CPU_exit`（:2451）、补票 `xa_CPU_update`（:3565）对 PERIOD 票**一律**走 `xa_CPU_entry_em / xa_CPU_exit_em / xa_CPU_update_em`——"em" 并非"员工专用"，**所有定期票（日票、定期票、员工票、公务票）共用同一套代码**。
- `CPU_GetFiles1d`（:913-995）被 7 处调用：进站 :2007、出站 :3193、补票 :3942、查询 :4574、激活 :6210、延期 :6443、以及各交易收尾的恢复重读 :2262/:2288/:3429/:3458/:4191。

### 文件1D 字段与位域布局（`xa_cpu20_operation.h:240-279`）

| 字节 | 内容 |
|---|---|
| 0 | actionSequenceNumber:4 \| productStatus:4 |
| 1 | validityStartDateTime_1:6 \| invoicePrinted:1 \| **activated:1** |
| 2-3 | validityStartDateTime_2:8 / validityStartDateTime:8 |
| 4-6 | **validityOrigin（有效区间-起始）** 与 **validityDestination（有效区间-终止）** |
| 7-12 | transactionSequenceNumber、lavSamId、lavValue |
| 13 | validityDuration_1:2 \| **validityDurationType:2** \| lavPaymentMethod:3 \| lavValue:1 |
| 14 | padding:3 \| **validityDuration:5** |
| 15 | checksum |

## 2. 第一部分：激活标志 / 有效区间 / 有效期 全量写卡路径审计

对 1D 的写卡只能通过 `xa_update_file_1d`（:6051-6123）。全仓库共有 6 处调用（另 1 处被注释）：

| # | 位置 | 场景 | 写什么 | 性质 |
|---|---|---|---|---|
| 1 | :984 | **20260715 修复块（CPU_GetFiles1d 内部！）** | durationType:=0x03(月)、duration:=0x18(24个月)、start:=读卡器当前时间 | **恶性修改** |
| 2 | :6310 | `xa_CPU_active_em` 首次使用激活 | activated:=1、start:=当前时间 | 正常业务（但有前提问题，见下） |
| 3-7 | :2269/:2295/:3436/:3465/:4198 | 交易收尾"恢复块" | 意图恢复 validityStartDateTime | **全部失效**（函数忽略参数，见 2.2） |
| — | :6287 | 激活-过期分支 | （写卡语句被注释掉） | 不写卡 |

### 2.1 恶性修改点：CPU_GetFiles1d 内的 20260715 块（:962-987）

```c
/************20260715判断员工卡有效期开始时间字段是否改变************/
xa_MinuteTolocaltime(&startbcdtime[0], tpfile05.cardBaseDateTime, tpfile1d.validityStartDateTime, &lnsecondtime);
if(tpfile1d.activated == 1 && (memcmp(tpCPU.time_bcd, startbcdtime, 4) < 0))
{
    tpfile1d.validityDurationType = 0x03;  //类型：月
    tpfile1d.validityDuration = 0x18;      //24个月
    ... /* 更新 _File1C 位域 */
    xa_localtimeToMinute(tpCPU.time_bcd, ..., &tpfile1d.validityStartDateTime);  // start := 读卡器时间
    memcpy(cpu_1d_data, xaFile1C.buff, 16);
    if(0 != (chCode = xa_update_file_1d(cpu_1d_data, out_buf)))
        return chCode;
}
```

**触发条件**：`activated == 1`（已激活）且 `读卡器时钟 BCD < 卡内有效期开始时间 BCD`（memcmp 只比较前 4 字节 = 世纪年月日 CCYYMMDD）。

问题清单：

1. **写卡发生在读函数里**。进站、出站、补票、查询、激活、延期、交易收尾重读——任何一次刷卡/查询都会先执行这段代码。读函数有写副作用，违反"读不写卡"的基本约束。
2. **触发条件依赖站级时钟**。`tpCPU.time_bcd` 直接来自上位机交易报文 `memcpy(tpCPU.time_bcd, &cmd_buf[6], 7)`（:1297/:2334/:3517/:4545/:5238/:6137/:6355/:6653），即**站级 PC 的时钟**。PC 时钟回拨一天、BIOS 掉电后日期错、未对时、跨年误设——任何"日期比卡激活日期早"的机器，都会把**每一张已激活定期票**改坏。
3. **修复值硬编码，原始时长被丢弃**。durationType/duration 被强制写成 3月/24个月，卡原有的时长（公务票可能是 1 天或短周期）没有任何地方保存，不可恢复。改完后卡变成"2 年通票"，与 1105 产品表的票种定义不符 → 后台判非法。
4. **无票种/乘客类型判断**。注释写"员工卡"，实际作用于全部 FEETYPE_PERIOD 票（日票、定期票、学生定期票等）。
5. **写卡无回滚保护、无流水同步**。写卡发生在 TAC 计算和 file17 交易记录提交**之前**，不经过 `tpMCPUProtect` 回滚机制。若写卡后交易失败或断电，卡内 1D 已改而 file17 无对应流水 → 后台核对不一致 → 判非法卡。
6. **checksum 字节不重算**。写回的 16 字节中 byte15 仍是读到的旧校验和（代码只有 :960 一处读 checksum，全仓库无重算逻辑）。严格校验的卡/后台会判文件非法。
7. **反向放大效应**：若某台时钟偏快的机器完成了激活（start 被写成未来日期），之后**全网任何一台正常机器**每刷一次就触发一次重写（start:=该机器时间、时长:=24个月）——自我放大、反复重写、无法自愈。

### 2.2 失效的"恢复块"（:2262-2270、:2288-2296、:3429-3437、:3458-3466、:4191-4200）

5 处恢复块的模式相同：

```c
if(beforeStartTransTime != tpfile1d.validityStartDateTime){
    xaFile1C._File1C.validityStartDateTime_1/2 = beforeStartTransTime ...;  // 只改 RAM 中的 buff
    memset(cpu_1d_data_end, 0x00, 16);
    memcpy(cpu_1d_data_end, xaFile1C.buff, 16);
    endChCode = xa_update_file_1d(cpu_1d_data_end, out_buffEnd);           // 传的是 cpu_1d_data_end
}
```

但 `xa_update_file_1d` 的实现在 :6087 写的是**全局缓冲**：

```c
char xa_update_file_1d(unsigned char *file_buf, unsigned char *out_buf)
{
    ...
    memcpy(&buf[13], cpu_1d_data, XA_CPU_1D_LEN);   // ← 用了全局 cpu_1d_data，没用参数 file_buf！
```

后果：恢复块精心构造的 `cpu_1d_data_end` **永远不会被写进卡里**，实际写卡的是全局 `cpu_1d_data`（即首次读到的旧快照）。恢复块是空操作。

### 2.3 激活标志与有效区间

- **激活标志**：全代码只有 `xa_CPU_active_em` :6297 一处写 `activated=1`（首次使用激活，正常业务）。没有任何路径能清除它。生产上"激活标志被改"最可能的是：(a) 20260715 块整文件写回时把与票种不符的时长写进去，后台把卡判为异常时连带归因；(b) 激活本身用了偏快的时钟，start 被写成未来 → 触发 20260715 链式重写。
- **有效区间（validityOrigin/Destination）**：解析在 :952-953，全代码**没有任何写卡路径修改区间**。整文件写回时区间字节来自刚读到的卡数据（round-trip 原样保留）。若生产观察到区间"被改"，需排查 1106 站区文件与卡内编码不一致（导致 `card_to_location`/`xa_ValidateArea` 拒绝或交易记录 vOrigin/vDestination 异常），而不是卡内字段被写。

## 3. 第二部分：上次修改（员工卡相关）的问题与遗漏

### 3.1 修改时间线（main.c:108-126 的 tp_ver 链）

| 版本 | 日期 | 内容 |
|---|---|---|
| 0x2200714 | 20250312 | 员工卡"有效期改变"日志（说明当时已发现字段被改） |
| 0x2210714 | 20250507 | 老年卡取消进出站超时 |
| 0x2220714 | 20250803 | **员工票有效期过期判断，更新相关字段** |
| 0x2260714 / 0x2270714 | 2025 | 4/5号线交易数据修复、优惠出站票超时判断 |
| 0x2280714 | 2025 | 修改员工卡有效期检查、进出站检查有效期（**当前正式版本号**） |
| 20260715 | 2026-07-15 | `CPU_GetFiles1d` 内新增"判断员工卡有效期开始时间字段是否改变"修复块，**未升版本号** |

### 3.2 20260715 修改的问题（核心）

1. **放错位置**：修复逻辑放进读函数 `CPU_GetFiles1d`，7 类操作路径全被波及（见 1 节调用清单）。
2. **触发条件用不可信时钟**：见 2.1-2。修复的本意是"发现 start 被改成未来时间的坏卡并修复"，但判断依据是读卡器自己的时钟；时钟一偏，合法卡全部误判。
3. **修复值凭空捏造**：不知道原始 duration 就硬编码 24 个月。正确的做法是查 1105 产品表按票种定义恢复，或只上报不修复。
4. **没有保护范围**：没有产品类型/乘客类型 guard，误伤全部定期票；没有"只修复一次"标记，同一张卡被反复重写。
5. **无流水与回滚**：写卡在交易提交之前、无 `tpMCPUProtect` 保护；checksum 不重算。
6. **未升版本号**：tp_ver 仍是 0x2280714，生产环境无法通过版本号区分是否包含该改动——这是"修复过的版本在生产上仍出问题"的运维层面直接原因（现场新旧固件混杂，无从追溯）。

### 3.3 配套"恢复块"的遗漏（与 20260715 块配套的防御逻辑）

1. **防不住要防的东西**：`beforeStartTransTime` 在第一次 `CPU_GetFiles1d` 之后才取值（进站 :2016、出站 :3202、补票 :3946），而 20260715 块的改写发生在 `CPU_GetFiles1d` **内部**——改写对恢复逻辑完全不可见，恢复块检测不到它。
2. **只恢复 start，不恢复 duration/type**：即使生效，时长被改成 24 个月的部分也恢复不了。
3. **因参数 bug 全部失效**：`xa_update_file_1d` 忽略 `file_buf` 参数（:6087），恢复块写的是旧快照全局缓冲，属空操作。
4. **修好参数 bug 反而引发新破坏**：若把 :6087 改为 `file_buf`，恢复块会把**首次使用激活（正常业务）**刚写上的 start 回滚成发卡时的未来截止时间、而 activated 保持 1 —— 下一台机器读到"已激活且 start 在未来"→ 触发 20260715 块 → 时长被改成 24 个月。也就是说这套防御逻辑与修复块互相咬合，形成新的破坏链。
5. 恢复块写回同样不重算 checksum。

### 3.4 其他遗漏

- `xa_CPU_active_em` 的"过期"分支（:6278-6289）先把 start:=now 写进**全局** `cpu_1d_data`（写卡语句被注释掉），全局缓冲被污染；由于 `xa_update_file_1d` 写的是全局缓冲，同一交易内任何后续写卡都会把这份被改数据写进卡。当前因该分支立即 return CE_EXPIREDDATE 尚未触发，但属于埋着的雷。
- 交易记录口径不一致：进站激活场景下，end_timebcd 用激活前的 start（:2020 的 lngHisecond1）计算、vStartDateTime 却用激活后的时间（`xa_CPU_active_em` 会改写调用方的 start_timebcd，:6293），单笔流水的 vStart/vEnd 与实际卡状态不一致，后台核对时易判异常。

## 4. 第三部分：生产环境根因分析（为什么"修复版"仍改坏字段）

### 根因链条

```
某台读卡器(站级PC)时钟异常（回拨/未对时/BIOS失电/误设日期）
        │
        ▼
该机器对已激活定期票(员工卡/公务票)执行任意操作(进/出/查/补)
        │
        ▼
CPU_GetFiles1d:962 触发：activated==1 且 机器时钟 < 卡内start日期
        │
        ▼
写卡：durationType:=0x03(月)、duration:=0x18(24个月)、start:=机器当前时间
（原始时长永久丢失；checksum 过期；无回滚、无流水）
        │
        ▼
卡时长与1105产品表票种定义不符 → 后台判非法/异常
（0x2200714 加入的"有效期改变日志"在后台侧记录到大量此类变更）
```

### 关键点

1. **"修复"就是破坏源**。20260715 块是为修复历史坏卡（start 被写成未来）而加，但：(a) 触发条件依赖不可信时钟 → 对合法卡大量误触发；(b) 修复值凭空硬编码 → 修完的卡必与票种定义不符 → 必被后台判非法；(c) 放在读函数里 → 每刷必执行。
2. **时钟是触发源**。`tpCPU.time_bcd` 来自上位机报文（:1297 等 8 处），全网只要一台机器日期偏慢一天，经过它的所有已激活定期票全部中招；若某台机器时钟偏快完成激活，则全网正常机器每刷必中招（start 永远在未来）。
3. **防御全部失效**。恢复块因"参数被忽略"成为空操作；checksum 无人重算；无回滚保护；无票种 guard。
4. **版本不可追溯**。20260715 修改未升 tp_ver（仍 0x2280714），"修复过的版本"与现场固件无法对应；仓库内历史 zip（V2220714/V226）与仓库二进制经 md5 比对均不匹配，现场存在多个版本的混跑，问题表现持续。
5. **为什么是"员工卡本站公务票"高发**：公务票刷卡频率高（员工每日多次进出站+查询），暴露在触发条件下的概率最大；且其票种定义对时长校验严格，被改成 24 个月后立刻判非法，现象最集中。

## 5. 修复建议（按优先级）

1. **立即删除/禁用** `CPU_GetFiles1d` 内 20260715 块（:962-987）的**写卡**部分。读函数禁止写卡。
2. 历史坏卡修复改为**只读检测+上报**：检测到"已激活且 start 在未来"时，记日志/回执错误码上报 ACC，由后台或专用修复指令（携带票种定义查 1105 后恢复正确的 duration/type/start）处理，禁止在交易路径硬编码修复值。
3. 修复 `xa_update_file_1d`（:6087）：`memcpy(&buf[13], file_buf, XA_CPU_1D_LEN)`；同时**重新评估恢复块是否保留**——若保留，必须配套修复（见 3.3-4 的连锁破坏说明），建议改为"写卡失败时按快照回滚"并纳入 `tpMCPUProtect`。
4. 所有 1D 写回路径（激活、恢复、任何未来新增）**重算 byte15 checksum**，并按卡规范生成。
5. 激活/任何"改卡"动作前**校验时钟可信性**：与 SAM/后台时间比对，偏差超阈值（如 >1 分钟或跨日）拒绝交易并告警，而不是改卡。
6. 版本管理：任何改动必须升 tp_ver 并留痕；对现场设备做版本普查，清理旧固件，统一到修复版。
7. 运维排查：全站上位机 NTP/对时机制（重点排查曾出现过时钟回拨、BIOS 掉电、日期误设的站点）。
