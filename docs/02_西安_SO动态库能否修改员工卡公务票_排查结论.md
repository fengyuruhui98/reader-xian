# 西安 SO 动态库排查：能否修改员工卡本站公务票字段

> 任务：1. 拉取刚推送上去的 SO 动态库；2. 查看拉下来的动态库，分析其中是否有可能修改员工卡本站公务票（CPU 文件 1D）的代码。
> 结论先行：**不能。SO 动态库是纯底层驱动/射频传输库，字节级证据三重确认它不包含任何卡片业务逻辑，无法修改员工卡公务票的激活标志、有效区间、有效期等任何字段。真正的改卡源头仍全部在 TP 程序（xa_cpu20_operation.c 的 0715 修复块及激活/写卡路径）里。**

## 二、动态库里有什么：224 个函数符号全量归类

对 .so 的符号表做全量解析，所有函数符号归类如下（无一例外全是驱动/传输层）：

| 类别 | 函数族 | 作用 |
|---|---|---|
| SPI/UART 传输 | `spi_*`、`spidev_*`、`uart_*` | 与 RC531 射频芯片、SAM 卡的物理通道 |
| RC531 射频驱动 | `rc_*`（rc_request/rc_anticoll/rc_select/rc_read/rc_write…） | 寻卡、防冲突、选卡、射频读写 |
| M1 指令层 | `mcmh_*`、`mcml_*`（Mifare Classic 认证/读写/加减值） | 仅 M1 卡片命令，与 CPU 卡无关 |
| ISO14443-4 传输 | `mifpro_*`（icmd / icmd_chain / icmd_nochain / ats / pps / wtx / ack）、`iso_block_transceve` | **APDU 字节流搬运**：把 TP 组好的命令字节发给 CPU 卡，把应答字节收回来 |
| SAM 串口转发 | `sam_*`、`linux_sam_*` | 把 TP 组好的 SAM APDU 经串口发给 PSAM 并回收应答 |
| UltraLight | `UL_Page_Read/Write` 等 | M0 卡命令 |
| 板级外设 | `ee_read/ee_write`（EEPROM）、`rtc_rd_time/rtc_wr_time`、`timer_*`、`led`、`watchdog` | 设备自身存储/时钟/指示灯，不碰卡片 |

全库 **没有任何**：文件 1D 操作、有效期/激活标志/有效区间字段处理、票种业务判断、MAC 计算（`cpu_cal_protect_mac`/`CPU_externauth` 均在 TP 侧 [hh_cpu_operation.c:73/331](..%2F3018-3030-TP%2Fhh_cpu_operation.c#L73)）。

## 三、字节级证据（三重确认）

**1. 业务字符串扫描 = 0**

| GBK 关键字 | 出现次数 |
|---|---|
| 公务（B9 AB CE F1） | 0 |
| 员工（D4 B1 B9 A4） | 0 |
| 本站（B1 BE D5 BE） | 0 |
| 有效期（D3 D0 D0 A7 C6 DA） | 0 |
| 激活（BC A4 BB EE） | 0 |

全库 674 条可打印字符串中无任何票务/业务字样。

**2. 写文件 1D 的 APDU 指令 = 0**

TP 侧 [xa_cpu20_operation.c:6089-6092](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6089-L6092) `xa_update_file_1d` 构建的写卡命令是：

```c
memcpy(&buf[8], "\x04\xd6\x00\x00", 4);
buf[10] = 0x1D | 0x80;               // 文件 1D
buf[12] = XA_CPU_1D_LEN + 4;         // 长度
memcpy(&buf[13], cpu_1d_data, XA_CPU_1D_LEN);   // 有效期/激活标志等字段数据
```

而 .so 全库字节扫描中，`04 D6`（CLA=04 的 update binary，正是文件 1D 写指令）**出现 0 次**。库中虽出现少量 `00 B0`/`00 D0`/`00 DC`/`00 D6`/`00 82` 两字节片段，逐一核对上下文全部是 ARM Thumb-2 指令流或数据表中的巧合字节（如 `00 0b 00 d6` 为 `movw` 立即数、`f3 01 00 15 …` 为 ADD.W 指令、`e5 00 82 e5 …` 为加密数据表），**没有任何一条是 APDU 指令表或卡片命令构造代码**。

**3. 符号集与历史生产库同族**

推送库与 20211107 生产备份 `SO\so\liblinux4418_493.so.20211107.3M` 对比：函数集仅差 `c_read_byte/c_read_bytes`、`mcmh_increment/cml_increment` 等命名级差异；与 2440 平台版本仅差平台相关函数。说明这次推送**没有引入任何新的业务代码**，与历史生产库是同一驱动家族。

## 四、结论

**员工卡本站公务票（文件 1D）的完整修改链路全部在 TP 程序内**：

```
TP: CPU_GetFiles1d 内 0715 修复块 / xa_CPU_active_em / xa_update_file_1d
    （构建 04 D6 指令 + cpu_1d_data 字段数据 + cpu_cal_protect_mac 算 MAC）
        ↓
TP: mifpro_apdu (hh_cpu_operation.c:812) → SO: mifpro_icmd → RC531 射频 → 卡片
```

SO 扮演的角色是**字节搬运工**：它收到的已经是 TP 组好的完整 APDU 字节流，它不认识文件 1D，不认识"有效期/激活标志/有效区间"，也没有任何写卡指令构造能力，因此**不可能修改员工卡本站公务票的任何字段**。

唯一与 SO 相关的风险不是"改字段"而是"写失败"：若 SO 传输层有缺陷，写卡会以 `CE_WRITE/CE_READ` 失败告终（写不进去），而不会静默篡改字段。生产环境员工卡公务票字段被改的问题，根源仍在 TP 程序（0715 修复块的误触发 + `xa_update_file_1d` 的 `cpu_1d_data` 全局缓冲 bug），与 SO 动态库无关。

**附带说明**：SO 源码树中唯一出现伪卡片响应（canned 0x70…9000 TLV 应答）的是 `SO\test.so\cos.c`，属实验室测试桩，不参与生产编译。

## 五、源码层审计（SO/so —— 动态库的编译源程序）

### 5.1 构建结构

`SO/so/` 是推送动态库的完整源码树。构建方式特殊：[global.h:122-134](..%2FSO%2Fso%2Fglobal.h#L122-L134) 把全部 12 个 .c 源文件直接 `#include` 进 global.c，Makefile 目标 `liblinux4418_493.so` 只编译 `global.o` 一个目标即产出整库（`-shared -o liblinux4418_493.so global.o`）。因此本目录源码与推送库的对应关系是确定的。

### 5.2 全部源码功能清单（逐文件审计）

| 源文件 | 内容 | 与卡片业务的关系 |
|---|---|---|
| global.c | 延时、`InitModule/CleanUpModule`、`rf_reset`、`set_card_type`、UL_*（UltraLight 读写）、`mcml_request2`（M1 寻卡）、设备 RTC 读写、设备 EEPROM 读写、看门狗、LED、`reader_get_version`、`mifpro_icmd` 外层封装 | 硬件初始化与外设，无卡业务 |
| iso_block.c | ISO14443-4 块协议：`iso_block_transceve`、`_mifpro_ats/pps`、`_mifpro_deselect`、`mifpro_wtx/noack/ack`、`mifpro_icmd_nochain/chain`、`_mifpro_icmd` | **纯 APDU 搬运**（见 5.4） |

| linux2440lib_uart.c / _cbuf.c / _timer.c | UART 驱动、环形缓冲、定时器 | 板级外设 |

### 5.3 源码层排查证据（全部为 0）

- GBK「公务/员工/本站/有效期/激活」等业务关键字：**0 处**
- `0xd6`/`\xd6`（文件 1D 写指令 update binary）任何形式：**0 处**（唯一含 "1D" 的是 RC531 寄存器地址 `REG_RC500_BPSK_DEM_CONTROL 0x1D`，巧合）
- 按 APDU 指令字节（INS）分发的 `switch/case`：**0 处**——整个库从不解释 APDU 内容
- MAC/DES 加密计算：**0 处**（grep 命中均为误报："DESELECT" 射频反选、"dest_block" 参数名）

### 5.4 三个核心传输函数逐一确认

1. **`_mifpro_icmd`**（[iso_block.c:900](..%2FSO%2Fso%2Fiso_block.c#L900)）：按 FSCI 把 TP 组好的 APDU 切成链式/非链式 I-block，加 PCB/CID 组帧发出；收响应后仅剥掉帧头偏移、重组链式响应、`memcpy` 原样返回载荷字节。**载荷内容零改动**。
2. **`sam_apdu_send`**（[linux2440lib_sam_int.c:903](..%2FSO%2Fso%2Flinux2440lib_sam_int.c#L903)）：在 TP 组好的 SAM APDU 前加 4 字节传输头（命令号/卡槽号/etu/wait_etu），经 DLE 组帧从串口发出。**不解析、不修改 APDU 内容**（长度校验仅限 5~251 字节的传输约束）。
3. **`sam_prot_gen_block`**（linux2440lib_sam_prot.c:53）：仅做 DLE 转义组帧，收发状态机不含任何语义。

### 5.6 源码层结论

SO/so 源码树与二进制证据完全互证：**动态库（无论源码还是二进制）都不具备修改员工卡本站公务票的能力**。它唯一做过的事是把 TP 程序组好的 APDU 字节流原样搬运到卡片/SAM，并把应答原样搬回。文件 1D 的"有效期/激活标志/有效区间"全部由 TP 程序（[xa_cpu20_operation.c](..%2F3018-3030-TP%2Fxa_cpu20_operation.c)）组织与写入。

**两个附带提醒（与公务票无关，但与生产稳定性有关）**：
1. SPI 速率 6MHz→2MHz 会降低射频吞吐（CPU 卡交易变慢），需确认是否有意为之；
2. `rc_wait_irq()` → `rc_wait_m1_auth_irq()` 仅影响 M1 卡认证路径，需回归验证 M1 卡（普通卡）认证成功率。
