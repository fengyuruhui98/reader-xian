# 西安员工卡公务票：时钟可信前提下的根源再分析

> 前提修正（接受用户两点事实）：
> ① 上位命令所带时钟可信 → 0715 修复块的触发比较本身是"诚实"的：只有卡片上有效期起始日期**真实处于未来**时才触发。排除"站机时钟偏移误触发"旧结论。
> ② 修复值（月型 0x03、24 个月）与公务票产品表一致，不是凭空捏造。排除"捏造修复值"旧结论。
>
> 结论：既然触发诚实、修复值正确，问题必然出在——**触发语义**、**写入记录本身的完整性**、**写入时机**、**回滚机制**这四个环节。0715 兜底块自身就是生产环境"字段被改"事件的最大制造者。

---

## 一、根源分析

### 根源 1：触发语义错误 ——「起始日期在未来」≠「被篡改」

触发条件（[xa_cpu20_operation.c:964](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L964)）：`activated == 1 && 卡上起始日期 > 当前时间`。

该条件**无法区分**以下三类卡，一律判为"被篡改"并强制执行修复：

| 类别 | 说明 | 修复的后果 |
|---|---|---|
| 合法未来生效票 | 后台发卡/延期时生效日期写为未来（如下月 1 日生效的公务票），激活标志已置位 | 把合法卡的生效日改写成"今天"，后台按发卡记录比对 → **判卡非法** |
| 老固件写坏卡 | 现场仍有旧版本固件机器在写未来起始日期（见根源 5） | 修复与老固件**互相覆盖**，卡被反复改写 |
| 真被篡改卡 | 修复块设计目标 | 修复值正确，但记录整体失效（见根源 2） |

### 根源 2：修复写入的记录整体失效 —— 校验和未重算

修复块修改了记录中的三组字段：
- 起始日期（byte1~3，validityStartDateTime 22 位）
- 有效期类型（byte13 的 2 位）
- 有效期时长（byte13/14）

但 **byte15 的 checksum 字段从不重算**（全代码库 3 处 checksum 引用均为读取，无一重算/校验）。修复值本身正确，但写入的记录整体校验和不匹配 → 后台/清算完整性校验失败 → 卡仍被判非法。**表现为"修过了、字段还是不对"。**

### 根源 3：无票种判断 —— 公务票的修复值被写进所有 1D 卡

FEETYPE_PERIOD 的全部票种（员工月票、公务票等）都走文件 1D 与同一套 entry/exit/update 函数。修复块**不判断产品 ID**，对任何触发的 1D 卡一律写"月型 0x03、24 个月"。对公务票正确，对其它票种就是把有效期写错 → 该卡按自身产品表被判非法。

### 根源 4：修复块嵌在"只读路径"里，且先于交易校验

`CPU_GetFiles1d` 被 5 类路径调用：进站（:2007）、出站（:3193）、更新（:3942）、**查询**（:4574，`xa_CPU_inquire`）、各恢复块的重读（:2262/:2288/:3429/:3458/:4191）。因此：

1. **纯查询交易也会写卡**——乘客在查询机上刷一下卡，卡就被改写了；
2. 修复写在 `xa_TellDate` 日期校验、区间校验、卡锁校验**之前**——一笔随后被拒绝的交易（区间不符/超时/卡锁），卡已经被改写；
3. 同一次交易内可多次触发（主读 + 恢复块重读）。

### 根源 5：老固件仍在现场 —— 版本号未变更，原始写坏源无法定位与清除

main.c 版本链（:108-126）到 `0x2280714` 为止，**20260715 修复块没有新增版本号**。后果：

- 现场新旧固件无法区分、无法统计、无法回收；
- 未来日期卡由老固件（或后台发卡）持续供给，新固件持续"修复"，**新旧机器互相覆盖**——这正是"被改的卡太多了、找不到原因"的机制性原因；
- 0x2200714（20250312 员工卡有效期改变日志）只能记录"有效期变了"，无法归因是谁改的——而修复块本身无任何日志（块内无 TestLog/PRINTK）。

## 二、兜底方案为什么没有起作用

### 1. 修复即破坏（根源 1~3）
兜底块的每次"修复"都会产生一个新的"有效期改变"事件：对合法卡动手、写校验和失效的记录、写错票种的有效期。监控日志里的事件不减反增。

### 2. 回滚机制结构性失效
恢复块（:2262-2270 / :2288-2296 / :3429-3437 / :3458-3466 / :4191-4200）本来的设计是：交易中发现起始日期变了，就把**交易前的原值**写回卡里。但它永远做不到：

- **参数 bug**：[xa_cpu20_operation.c:6087](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6087) `xa_update_file_1d` 忽略 `file_buf` 参数，恒写全局 `cpu_1d_data`。恢复块把原值放进局部 `cpu_1d_data_end` 再调用，实际写入卡的却是全局——而全局刚被恢复块自己的 `CPU_GetFiles1d` 重读刷新为**当前记录**。回滚写的是"当前值"而非"原值"，**恒为空转**；
- **基准取值错误**：`beforeStartTransTime` 在 :2016（主读 `CPU_GetFiles1d` 之后）才取值。若 0715 块已在主读中触发，基准已经是**修复后的值**——即使回滚机制修好，滚回去的也是错误值；
- 触发比较 `beforeStartTransTime != tpfile1d.validityStartDateTime` 在主读未触发修复时恒为相等 → 恢复块在绝大多数交易中根本不会进入写卡分支——**回滚是死代码**。

### 3. 触发条件自锁
`activated == 1 && 起始日期在未来` 把两类最需要修的卡排除在外：
- 激活标志已被清零的卡（生产症状之一）→ 永不触发 → 永远修不了；
- 起始日期被改到过去的卡 → 不触发。

### 4. 修复写卡失败即拒交易
[:984](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L984) 修复写卡失败直接 `return` 错误码 → 交易被拒、卡未修复；下一次触碰再次触发再次写 → 每笔交易都在尝试写卡。

### 5. 无日志、无版本号 → 无法归因、无法评估
修复块无任何日志输出；版本号未 bump。生产侧看到的只是"卡又被改了"，既无法确认修复是否生效、也无法统计老固件占比。

## 三、结论

**一句话**：0715 兜底块是一个"嵌在只读函数里、先于交易校验、不分票种对所有 1D 卡生效、不重算校验和、且回滚失灵的写卡器"。它把合法未来生效票和老固件坏卡统一改写成"校验和失效 + 可能错票种"的记录，成为生产环境"有效期/激活标志等字段被改"事件的**最大制造者**；而 0715 之前的原始写坏源，经代码遗迹还原正是本代码库自己的"先改卡、再拒绝"过期分支（见新增第五章），其中一条（xa_CPU_defer :6427）至今仍是活跃代码。生产上另一个高频症状"0x3 非法卡"则来自一条**独立的**机制——进站黑名单静默锁卡（check_metro_Black_Lock 把文件 15 的 cardStatus 写成非 1），报错码由 TP 自己的 :1324 检查返回、与后台无关、也与 0715 块无关（见新增第六章）。

## 四、修复建议（按优先级）

1. **收窄触发**：触发后先判产品 ID/产品表与发卡记录，仅对确认被篡改的卡执行修复；未来生效票直接放行；
2. **重算校验和**：任何 1D 写路径（含修复、激活、回滚）写入前重算 byte15 校验和；
3. **移出只读路径**：修复动作从 `CPU_GetFiles1d` 移出（至少移出查询路径），放到交易校验通过之后、TAC 计算之后执行；
4. **修 :6087 参数 bug**，恢复回滚写原值的能力；`beforeStartTransTime` 基准在修复前取值；
5. **修复块加 TestLog + 版本号 bump**（新 tp_ver），用于归因与覆盖率统计；
6. **统计并回收现场老固件**，切断未来日期卡的供给源；
7. **处置漏网的活跃写卡**：注释或删除 [xa_CPU_defer TIMES 分支](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6427) 的 `xa_update_file_1c` 写卡，并补上写卡后的 `return`（当前写卡成功后会 fall-through 落进 PERIOD 分支对多程卡去读 1D 文件，随后 `default: return CE_NON_FEETYPE`——"先改卡、后报错"）；同时全局核对所有 `xa_update_file_1[cd]` 调用点，确认无其它漏网。
8. **修复黑名单锁卡链路（"0x3 非法卡"的源头）**：[check_metro_Black_Lock](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6461) 二分查找上界 :6475 改为 `blacknum - 1`；1104 下载解析后清零新缓冲；进站 blnBlock=0 写卡分支（:6565-6574）加日志；与后台核对 1104 cardStatusCode 语义（写 1 锁卡不可见、写 2/3 导致下一笔 0x3）。详见第六章。

## 五、0715 之前的大量写坏是怎么来的（历史成因还原）

> 问题：0715 修复块是 2026-07-15 才加上的，在那之前生产上"很多卡被写坏"是为什么？
> 结论先行：**不是外部攻击，也不是时钟偏移——是读卡器自己的"先改卡、再拒绝"过期处理分支**。代码遗迹（被注释的写卡语句）证明这些写卡曾经生效；其中一条至今仍是活跃代码。

### 5.1 写坏主源：「先改卡、再拒绝」的过期处理分支

1C（多程）/ 1D（员工票、公务票等期票）的激活函数中各有一个"过期分支"：当 `当前时间 > 起始日期`（票已过期且未激活）时，原逻辑为：

1. 把记录里的起始日期改成**当前时间**（`xa_localtimeToMinute(tpCPU.time_bcd, ...)`）；
2. 把改后的 16 字节记录**写回卡**（`xa_update_file_1c/1d`）；
3. 然后返回 `CE_EXPIREDDATE` **拒绝交易**。

代码遗迹（写卡语句的当前状态）：

| 位置 | 票种 | 调用场景 | 写卡状态 |
|---|---|---|---|
| xa_CPU_active_cnt :6237-6238 | 1C 多程 | 进站激活 | **被注释**（`//if(...xa_update_file_1c...)`） |
| xa_CPU_active_em :6287-6288 | 1D 期票 | 进站/更新激活 | **被注释**（`//if(...xa_update_file_1d...)`） |
| **xa_CPU_defer TIMES 分支 :6427** | 1C 多程 | 延期命令（[xa_operation.c:489](..%2F3018-3030-TP%2Fxa_operation.c#L489) 分发） | **至今活跃**，且写卡成功后**没有 return，直接 fall-through 落进 PERIOD 分支** |

被注释的两处本身就是"曾经生效"的证明——注释动作即某次修复的一部分（对应 0x2280714"修改员工卡有效期检查"）。而 xa_CPU_defer 里的同款写卡**漏网未被注释**：现场只要对一张过期未激活的多程卡执行延期命令，读卡器就先把起始日期改写为"今天"写进卡，随后流程落进 PERIOD 分支去读 1D 文件（多程卡多半读不到）→ 命令报错返回。**卡被改了，命令还被拒了。**

危害机制（为什么是"很多卡"）：

1. **卡被拒但已被改**：操作员/乘客以为操作失败，卡却已经变了；
2. **起始日期逐次前移（ratchet）**：下次触碰时 `now > start(上次触碰日)` 依然成立 → 再写一次 → 起始日期被一次次推到触碰当天，后台看到的是一张起始日期不断变化的卡；
3. 后台按发卡记录比对 → 发现"有效期被改"（对账层面）。闸机上显示的"0x3 非法卡"报错则是读写器 TP 自己的判断（进站 [xa_cpu20_operation.c:1324](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L1324) 检查 cardStatus），不是后台——机制见第六章；
4. 1D 的同类路径（被注释前）对员工票/公务票同样生效，作用在闸机高频交易的进站/更新激活路径上，覆盖面远大于延期命令。

### 5.2 激活分支对"未来生效票"的改期

else 分支（`now <= start`，票未过期）：激活并写卡时起始日期被改成"今天"（:6262 1C / :6310 1D，至今活跃）。对发卡时起始日期为未来的票（如下月生效），首次触碰就把生效日提前到今天 → 与后台发卡记录不符 → "有效期改变"。这是设计行为，但恰恰在生产上持续制造"字段被改"事件——也解释了 0x2200714 日志在 0715 之前就报警的原因之一。

### 5.3 为什么坏卡越积越多：恢复块从设计上就是空转

被 5.1/5.2 改坏的卡，理论上应由恢复块（"发现起始日期变了就写回原值"）兜底——但如第二章 2 节所述，恢复块因 :6087 参数 bug（恒写全局 `cpu_1d_data` 而非传入的原值缓冲）+ 恒等比较死代码而**空转**。改坏无人修复 → 坏卡只增不减 → "很多卡被写坏"。

### 5.4 时间线还原（版本链 + 代码遗迹互证）

| 时间 | 版本 | 事件 |
|---|---|---|
| 2023-07-14 | —（无版本号） | 恢复块区域加入 `memset(cpu_1d_data,0x00,16);//20230714` 共 8 处、测试日志缓冲 `str2023/buf2023` 同日引入 → 团队自 2023 年 7 月起就在 1C/1D 读写区域反复打补丁 |
| 2025-03-12 | 0x2200714 | "员工卡有效期改变日志" → 有效期被改现象已被生产观测 |
| 2025-08-03 | 0x2220714 | "员工票有效期过期判断，更新相关字段" → 过期分支的"更新字段（含写卡）"行为在此版本前后活跃 |
| 2025-10 ~ 2026 | 0x2260714 / 0x2270714 / 0x2280714 | 0x2280714"修改员工卡有效期检查，进出站检查有效期" → 过期分支写卡被注释（:6237 / :6287），但 xa_CPU_defer 的 :6427 **漏网** |
| 2026-07-15 | （无版本号） | 加检测修复块 |

### 5.5 为什么 0715 块修不掉这些卡

1. **方向不匹配**：5.1/5.2 产生的坏卡起始日期 = 触碰当天（相对后来是过去），而 0715 块只修"起始日期在**未来**"的卡 → 触发不到；
2. **激活标志被清零的卡（activated==0）永不触发**；
3. **旧固件仍在现场**（写卡未注释的版本，无版本号无法区分/回收）→ 继续制造新坏卡；
4. 而"起始日期在未来"的卡里混着**合法未来生效票**——0715 块把它们误修了（第一章根源 1），结果是一边修不上旧坏卡、一边把合法卡写坏。

### 5.6 小结

0715 之前"很多卡被写坏"的根源是**读卡器自己的激活/过期处理代码在拒绝交易之前先写卡**（0x2220714 时代"过期判断、更新相关字段"设计的遗留），叠加**恢复/回滚机制恒为空转**导致坏卡无法自愈、越积越多。附带说明：生产症状中"激活标志被清零"在本代码库当前路径中无对应写源（激活路径只置 1 不清 0），更可能来自更早固件版本或后台操作；但"有效期起始日期被改"有上述确凿写源。这一结论也修正了此前"原始写坏源=老固件"的笼统说法：**写坏源就在本代码库的过期/激活分支里，其中一条（xa_CPU_defer :6427）至今仍是活跃代码**。另外，用户指正"非法卡（0x3）是读写器 TP 返回的、不是后台判断的"——该症状的机制（黑名单静默锁卡改写文件 15 的 cardStatus）已还原，见第六章；它与第五章的写坏源是两条独立机制。

## 六、0x3 非法卡：读写器 TP 自己返回的（黑名单静默锁卡机制还原）

> 用户指正（原话要点）：非法卡是读写器 TP 返回的，不是后台判断的；正常进出之后，下一次进站可能就被改写了，报 0x3 非法卡。
> 结论先行：**0x3 = CE_CARDSTATUS，判定点是 TP 进站函数对卡上文件 15 的 cardStatus 字段的检查（:1324）。全代码库中能把该字段写成"非正常"的只有一个写源——进站黑名单检查 check_metro_Black_Lock 的"静默锁卡"分支（blnBlock=0）。被锁卡后的下一笔触碰（换闸机重试、出站、或再下一次进站）即报 0x3。与 0715 修复块无关**（0715 只写文件 1D，0x3 是文件 15 的症状）。

### 6.1 0x3 的判定点全在 TP 内

- 错误码 [xa_error_code.h:24](..%2F3018-3030-TP%2Fxa_error_code.h#L24) `CE_CARDSTATUS 0x03` = "卡片状态是否正确"（[xa_name.c:187](..%2F3018-3030-TP%2Fxa_name.c#L187)）；
- 判定代码 `if(tpfile15.cardStatus != 1) return CE_CARDSTATUS;` 位于：
  - 进站 [xa_cpu20_operation.c:1324](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L1324)（注释 `//not locked status`）
  - 出站 :2364、出站(期票) :3535、更新/充值入口 :5268
  - 查询 :4658/:4719/:4775 把 cardStatus 放进 `out_buf[88]`，:4865 `if(out_buf[88] != 1)` → CE_CARDSTATUS
- cardStatus = 文件 15（SFI 0x15）字节 0 的低 4 位（[xa_cpu20_operation.h:130-131](..%2F3018-3030-TP%2Fxa_cpu20_operation.h#L130-L131) `rfu1:4 | cardStatus:4`）。取值语义（同平台约定，[xa_ul_operation.h:11-14](..%2F3018-3030-TP%2Fxa_ul_operation.h#L11-L14)）：`0=RFU / 1=正常(not-locking) / 2=锁 / 3=回收`——**正常卡 = 1**；
- **全库 grep 结论：`tpfile15.cardStatus` 的赋值只有 4 处**——:779（读卡）、:6507（黑名单二分命中）、:6528（区段黑名单命中）、:6565（锁卡写卡前）；`xaFile15._File15.cardStatus` 的修改只有 :6565 一处。**唯一能把卡上 cardStatus 改成非 1 的代码 = check_metro_Black_Lock**（进站/出站的正常写路径都先读卡再 `memcpy(cpu_15_data, xaFile15.buff, 13)` 原样保留该字节；0715 修复块只写文件 1D）。

### 6.2 唯一写源：进站黑名单"静默锁卡"（[check_metro_Black_Lock :6461](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6461)）

- 全库只有两个调用点：
  - 进站 [xa_cpu20_operation.c:1328](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L1328) `check_metro_Black_Lock(lngLogicID, 0, ...)` —— **blnBlock=0，命中后写卡**；
  - 查询 :4850 `check_metro_Black_Lock(lngLogicID, 0xff, ...)` —— blnBlock=0xff，命中只拒绝、**不写卡**。
- 命中后的动作序列（blnBlock=0 分支，:6546-6634）：
  1. :6565 `xaFile15._File15.cardStatus = tpfile15.cardStatus`（黑名单条目的 cardStatusCode，非 1 值）；
  2. :6566-6571 **顺带把起始日期改写为"今天"、lastLocation 改为本站**——"卡被改写"的另一半症状（与第五章 5.1 同一类改写）；
  3. :6573-6574 把改后的记录写回卡上文件 15（[xa_update_file_15 :5755](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L5755)，`04 D6 95 00` + MAC）；
  4. :6577-6602 追加文件 17 黑名单交易记录（transactionType=7）；
  5. :6604-6630 生成 TxnCardBlock 黑名单交易记录（SAM 算 MAC）塞进 out_buf 返回给站机，reasonCode = 写入的 cardStatus；
  6. :6632 `reader_status = XA_RW_RECORD`；:6634 **返回 CE_BLACKLIST（0x01）**。
- :6542 注释 `//not block card only display message`：该分支的设计意图是"只提示、不拦人"——站机 PC 收到 0x01 + 一条黑名单交易记录后可按策略放行。因此**被写卡的那一笔进站，乘客视角可以近似"正常"**；
- 此后卡上 cardStatus ≠ 1，**任何触碰**（进站 :1324 / 出站 :2364 / :3535 / 查询 :4865 / 更新 :5268）都由 TP 直接返回 0x3——正是"非法卡是读写器 TP 返回的，不是后台判断的"。

### 6.3 正常卡为什么会被命中（三种误命中机制）

**A. 二分查找上界 off-by-one + 名单收缩残留（代码 bug 级）**
- :6475 `lngCSCHighIndex = tpBlacklist1104.CardBlack_val.blacknum;`——blacknum 是**个数**（[binEOD.h:420](..%2F3018-3030-TP%2FbinEOD.h#L420) "黑名单卡数量"），上界应为 `blacknum - 1`；
- 当卡号大于所有有效条目时，low 一路右移到 low=high=blacknum，:6493 循环**多执行一次**，读 `CardBlacklist_val[blacknum]`——越界槽位；
- [bin_file_manage.c:712-730](..%2F3018-3030-TP%2Fbin_file_manage.c#L712-L730) 每次 1104 下载：free 旧缓冲 → malloc 新缓冲 → **只 fread 前 blacknum 条，无清零**。堆上同址复用（free 后 malloc 等尺寸/更小尺寸，几乎必复用同一块）→ 越界槽位残留**上一次更长名单**的旧条目；
- 若残留条目 CardID == 本卡号 → **已被移出黑名单的卡继续被命中**（名单收缩时，旧名单第 blacknum 条恰好是这只"幽灵卡"；每次名单变化"幽灵"换人）；
- 附带：名单必须按 CardID 升序（[binEOD.h:408](..%2F3018-3030-TP%2FbinEOD.h#L408) 注释要求），若后台下发未排序数据，二分查找失效、行为不可预测。

**B. 区段黑名单区间误伤（数据级）**：:6524-6525 `logicID ∈ [StartCardID, EndCardID]` 即命中；若后台下载的区段覆盖了正常员工卡号段（批量排查、数据错误、或有意区段锁定），**整个号段的卡在下次进站全部被静默锁卡**。

**C. 真黑名单命中（设计行为）**：挂失/冻结等卡，写锁 + 记录 + 0x01 是预期功能。

### 6.4 与"正常进出之后，下一次进站报 0x3"的对齐

一次典型事件的时间线：

1. 第 N 次行程正常：cardStatus=1，未命中（名单未更新 / 未误命中）；
2. 期间 1104 名单更新（收缩出"幽灵槽位"、或新增覆盖本卡号段的区段、或本卡真被挂失）；
3. **下一次进站**：TP 命中 → 静默锁卡写卡（cardStatus≠1 + 起始日=今天）→ 返回 0x01，站机按"只提示不拦"策略放行，或乘客换闸机；
4. **从下一笔触碰起**（换闸机重试、出站、或再下一次进站）：:1324 → CE_CARDSTATUS **0x3 非法卡**，由 TP 直接返回。

关键点：**写卡的那一笔返回的是 0x01 黑名单；0x3 是之后每一笔触碰的 TP 判定**——两者在站机日志上是连续的，正好呈现为"正常进出之后，下一次进站就被改写了，报 0x3"。

补充（cardStatusCode 取值语义）：若后台发的 cardStatusCode 恰好是 1（1104 规范 [binEOD.h:411-412](..%2F3018-3030-TP%2FbinEOD.h#L411-L412) "锁卡时写入票卡的锁卡状态：1:遗失/被盗；2:其他原因"），写入值等于正常值 → **状态层锁卡不可见（不会出 0x3）**，但 :6566 的"起始日=今天"改写照发生——此时症状表现为"卡被改（有效期变了）"而非 0x3；写 2（其他原因）或 3（回收）则下一笔必报 0x3。两种取值正好解释生产上"被改写"与"0x3"混合出现的现象。

### 6.5 与 0715 修复块的关系（两条独立机制）

- 0x3 的判定对象是**文件 15**；0715 修复块只写**文件 1D**（`04 D6 9D 00`）→ **0715 块不可能直接产生 0x3**；
- 两条机制共享一个汇聚点：:6566 把起始日期改成"今天"——与第五章 5.1 过期分支同一类改写。对账系统看到的"有效期被改"事件，一部分来自黑名单锁卡而不是 0715 块；
- 修正第五章的说法：5.1 第 3 点"后台判卡非法"已精确化为——后台按发卡记录比对发现"有效期被改"（对账层面）；闸机上显示的"0x3 非法卡"是 TP 的 :1324 判断（交易层面），不是后台。

### 6.6 修复建议（追加）

1. :6475 上界改为 `blacknum - 1`（或循环条件 `lngCSCLowIndex < lngCSCHighIndex`），消除越界读残留槽位；
2. 1104 解析在 malloc 后 `memset` 清零，或严格按 blacknum 使用，保证名单收缩后残留不可达；
3. 进站 blnBlock=0 写卡分支（:6565-6574）加 TestLog/PRINTK——目前整条锁卡链路**无任何日志**（唯一打印在 `DEBUG_1104_PRINT` 宏里，仅限名单下载时）；
4. 区段黑名单下载前与发卡号段做交叉校验，杜绝区间误伤；
5. 与后台核对 1104 cardStatusCode 取值语义：写 1 会让锁卡在状态层不可见（等于正常值），写 2/3 导致下一笔 0x3——需按预期效果约定并验证。

### 6.7 闸机返回 03、BOM 分析返回 0x08：两个不同字段的判定

> 生产观察：闸机上位机返回 03；BOM 分析返回 0x08"卡状态非法"。两码在本 TP 代码里是**两个不同文件、两个不同字段**的判定：

| 码 | 名称（[xa_name.c:187/207](..%2F3018-3030-TP%2Fxa_name.c#L187-L207)） | 判定对象 | 判定位置 | 本代码库内的写源 |
|---|---|---|---|---|
| 0x03 CE_CARDSTATUS | 卡片状态非法（"卡片状态错"） | **文件 15** 字节0 低4位 cardStatus ≠ 1 | 进站 :1324、出站 :2364/:3535、查询 :4865（out_buf[88]）、更新 :5268 | **check_metro_Black_Lock 静默锁卡（:6565-6574）** |
| 0x08 CE_LOCKED_TICKET | 产品状态非法（"已锁卡"） | **文件 1D** 字节0 高4位 productStatus ≠ 1（[xa_cpu20_operation.h:240-241](..%2F3018-3030-TP%2Fxa_cpu20_operation.h#L240-L241)） | 查询 :4842（out_buf[58]=tpfile1d.productStatus :4644）、更新 :3995、充值 :5165、激活 :6182/:6198/:6214、延期 :6400/:6416/:6447 | **无（全库 grep：productStatus 只读不写）** |

要点：

1. **两码都是 TP 自己返回的**，不是后台判断——与用户的指正一致；
2. 闸机 03 的链条已在 6.2 还原（黑名单锁卡写文件 15）；
3. **文件 1D 的 productStatus 在当前源码内没有任何写源**：文件 1D 的全部写路径（0715 块 :984、恢复块 :2269/:2295/:3436/:3465/:4198、激活 :6310）都是从刚读回的原值整块 `memcpy`，productStatus 恒被原样保留（`xa_update_file_1c/1d` :5977-6123 只把全局 `cpu_1c_data/cpu_1d_data` 打包进 0x04D6 写命令，而这些全局唯一被读卡成功后的响应填充，见下）；进站/出站路径**根本不检查也不写** productStatus；
4. 对**全部历史固件**（v217/v219/v220/v221/v2220714/v226、2022 年 GPO-capp、2023、2024-08-07 部署版）做了 ARM 反汇编级写者普查，结论一致：**任何版本、任何函数都没有写过文件 1D 的字节0**（详见 6.8）；
5. 因此 BOM 的 0x08 只有两条可能路径，而它们**同根**——见 6.8 的完整裁定。

### 6.8 BOM 0x08 写源裁定：全版本反汇编普查 + 卡内联动锁定

#### 6.8.1 两码的判定顺序差异（为什么同一张卡闸机报 03、BOM 报 08）

| 流程 | 判定顺序 | 结果 |
|---|---|---|
| 闸机进站 [xa_CPU_entry :1267](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L1267) | ① :1319 读文件 15 → ② :1324 `tpfile15.cardStatus != 1 → return CE_CARDSTATUS`（**先**）→ ③ :1328 黑名单检查 | 文件 15 先坏 → **0x03** |
| BOM 查询 [xa_CPU_inquire :4620](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L4620) | ① :4570/:4574 读文件 1C/1D → ② :4644 `out_buf[58]=tpfile1d.productStatus` → ③ :4840 `if(out_buf[58]!=1) return CE_LOCKED_TICKET`（**先**）→ ④ :4865 `if(out_buf[88]!=1) return CE_CARDSTATUS` | 文件 1D 先坏 → **0x08** |

同一张卡**两个文件都受损**，闸机与 BOM 只是各自先查了不同的文件而已——这要求一次事件同时破坏文件 15 与文件 1D。

#### 6.8.2 文件 1D 写入者的全版本普查（ARM 反汇编）

方法：以 16 字节连续加载/存储（copy16）特征定位各版本 `xa_update_file_1d`，再对全部 .text 做 BL 调用者扫描，逐个反汇编写者函数核对**是否触碰字节0**。

| 固件版本 | 文件 1D 的全部写者 | 写者实际改动的字节 | 触及字节0？ |
|---|---|---|---|
| v217 / v219 / v220 / v221 / xian_station / 2023 | xa_CPU_active_em（激活） | 字节1/2/3（起始时间）+ 字节1 bit7（activated=1） | **否** |
| **2024-08-07 部署版** | xa_CPU_active_em @0x44454（+调度器 @0x448e0 仅做 `activated==1 → 0x08` 检查，不写） | 同上 | **否** |
| v2220714 / v226 | ① xa_CPU_active_em；② **独有的"有效期修复"函数**（v226 fn 0x33148 / v2220714 fn 0x38858，各 6 个以上调用点，全在 APDU 读+校验流程内） | ② 只改字节13/14（validityDurationType=0x03、validityDuration=0x18） | **否** |
| 2026 当前源码 | ① 激活 :6310；② 0715 修复块 :984；③ 恢复块 ×5（:2269/:2295/:3436/:3465/:4198） | ①②只改字节13/14与字节1/2/3；③ 只回写起始时间 | **否** |

关键结论：

1. **没有任何版本、任何函数写过文件 1D 的字节0**。激活函数（GPO-capp 0x4b2b4/0x4b564、2024 版 0x441b0/0x44454）逐字节核对过：只写字节1/2/3，字节1 |= 0x80；v226 修复函数 0x33148 只做字节13/14 的读-改-写（提取 2bit/5bit 有效期字段写回），其余字节整块透传——它就是 **2026-07-15 修复块 :962-987 的祖先**（同样置 `validityDurationType=3、validityDuration=24`）：2022-07 的 v2.22 引入、v2.26 仍在、2024 部署版已删除、2026 又换了触发条件加回。
2. **所有写卡都先读卡成功**：写者函数之前必经 `CPU_GetFiles1c/1d`（:855-995），SW=9000 校验失败即 `return CE_READ`，写路径根本到不了；写入数据整块来自刚读回的卡内原值（update 函数 :6013/:6087 只认全局 `cpu_1c_data/cpu_1d_data`，这两个全局唯一被读卡成功的响应填充）。
3. 因此 **TP 固件（含部署版与全部历史版本）从机制上造不出 productStatus≠1**——排除"写坏"来自 TP 写卡的可能，也排除 v226 修复函数误伤的可能（它最多写坏有效期，不会产生 03/08）。

#### 6.8.3 剩下的唯一写者：卡内 Applet 的联动锁定

文件 1D 的 productStatus 只剩两个可能来源：发卡初始化（只会写 1=NOTLOCK，否则卡第一天就过不了闸机）和**卡内 Applet 自己**。TP 源码 :4839 的注释本身就是规格证据：

```c
//product status:1-NOTLOCK;4,8,9,10-LOCK
if(out_buf[58] != 1) { out_buf[2] = out_buf[3] = CE_LOCKED_TICKET; ... }
```

productStatus 的锁定值 **4/8/9/10** 是卡规格里定义好的锁定编码——这些值没有任何 TP 代码写、发卡不会写，**只可能由卡内逻辑在锁定事件发生时写入**。

而现场唯一的锁定事件就是第六章还原的黑名单静默锁卡：进站 [check_metro_Black_Lock :6565-6602](..%2F3018-3030-TP%2Fxa_cpu20_operation.c#L6565) 用专有受保护写命令 `0x04 0xD6 0x95 0x00 + 16字节 + 4字节MAC`（:5789-5803）把误命中条目的 cardStatus 写进**文件 15**，并追加**文件 17 锁卡记录**（transactionType=7，含锁卡时间/站点，:6577-6602）。

推断：卡内 Applet 收到文件 15 的锁定写入后做**联动锁定**——同步把票文件 1D 的 productStatus 置为锁定值（4/8/9/10 之一）。这是安全卡的标准设计（卡状态被锁后必须让所有交易入口快速失败）。于是：

```
一次误命中（第六章三种误命中机制之一）
  → TP 写文件 15 cardStatus=锁定值（0x04D6-0x95 专有命令）
  → 卡内 Applet 联动写文件 1D productStatus=锁定值
  → 闸机下次进站：先查文件 15 → 0x03
  → BOM 查询：先查文件 1D → 0x08
```

**一次事件、两个文件、两个码，同一根因。** 这同时解释了为什么"正常进出之后的下一次进站"才开始报错、为什么 0715 修改前就有大量坏卡（与 0715 修复块完全无关）、以及为什么在 TP 代码里永远找不到 productStatus 的写源。

#### 6.8.4 现场判别方法（三分支）

在 BOM 上把问题卡做全字段读出，依次核对：

1. **文件 17 是否含锁卡记录**（transactionType=7，含锁卡时间/站点）——这是"是否发生过锁卡事件"的直接物证，可与卡最后一次正常进出记录对照时间/站点；
2. **文件 15 字节0 低4位 cardStatus**：≠1 → 第六章锁卡成立；
3. **文件 1D 字节0 高4位 productStatus**：
   - = 1 → BOM 的 0x08 是 BOM 固件对 cardStatus≠1 的错误码编号，与闸机 03 同根因（黑名单锁卡）；
   - = 4/8/9/10（锁定编码）→ 卡内联动锁定已发生，同上根因，且 productStatus 的取值本身就是锁定事件发生的规格级证据；
   - ≠1 且不是锁定编码 → 与锁卡无关的写源（发卡/其它设备异常），需另案追查。

#### 6.8.5 对修复方案的影响

- 0x08 不需要新的修复代码——修掉误命中锁卡（6.6）就从根上消除了 03 与 08；
- 已坏卡的解锁：需发卡系统/卡厂商支持"恢复卡状态"流程（把文件 15 cardStatus、文件 1D productStatus 复位为 1），TP 侧无此能力也不应新增（写 productStatus 反而是新风险）；
- 建议与卡厂商确认 Applet 在收到 0x04D6-0x95 锁定写入时是否联动写 productStatus；若有，可要求改为"仅记录、不联动"或提供解锁命令。

| BOM 判定文案 | "产品状态非法"（结果码 08） | — | 与 TP 查询路径 :4840 一致 |

三点验证结论：

1. **productStatus = 09，恰好落在 TP 源码注释的锁定编码集合 {4,8,9,10} 之内**——命中 6.8.4 判别分支②（卡内联动锁定已发生）。TP 全版本写不出非 1 值、发卡初始化只写 1（否则这张卡 2023 年就过不了闸机），排除法后只剩卡内 Applet 在锁定事件时写入。09 本身即锁定事件发生的规格级证据；
2. **cardStatus = 04 ≠ 1**——文件 15 确实被写坏，写入值 04 正是误命中名单条目的 cardStatusCode（第六章机制的预期产物，check_metro 把条目状态码原样写进文件 15 :6507/:6528/:6565）；
3. **时间线自洽**：该卡 2026-08-14 11:13 仍在正常交易（旅程开始/上次交易时间均为此刻），此后被锁——与"正常进出之后的下一次进站报 03"完全吻合。

至此 0x08 根源闭环：**一次误命中锁卡事件（第六章）→ TP 经 0x04D6-0x95 写文件 15 cardStatus=04 → 卡内 Applet 联动写文件 1D productStatus=09 → 闸机下次进站先查文件 15 报 03、BOM 查询先查文件 1D 报 08。两个码同根。**

最后一件可选物证：BOM 的"卡片历史交易记录"（文件 17/1A 区）中应有一条 transactionType=7 的锁卡记录（时间 2026-08-14 11:13 前后、站点=锁卡站点、reasonCode=04），现场可进一步核对坐实。

### 7.2 P0 止血（固件侧，单版本完成）

**7.2.1 黑名单误命中三源修复（#1、#2、#3）**
- `:6475` `lngCSCHighIndex = tpBlacklist1104.CardBlack_val.blacknum;` → `blacknum - 1`；`blacknum == 0` 提前返回不进入查找。
- [bin_file_manage.c:712-730](../3018-3030-TP/bin_file_manage.c#L712) 下载处理：`malloc` 后立即 `memset` 清零；`fread` 实际长度不足 `blacknum` 条时整表作废并告警日志（宁可不锁，不可误锁）。
- 区段命中（:6520-6532）加两条防线：区间非法（Start > End）直接跳过；命中时输出 TestLog（区间值、卡号、命中机制），供后台核对名单数据。
- 名单解析时校验升序，乱序名单告警（防御性）。

**7.2.2 锁卡动作显式授权化 + 全链路日志（#4）**
- 进站调用点 [xa_cpu20_operation.c:1328](../3018-3030-TP/xa_cpu20_operation.c#L1328) 传 `blnBlock=0`（可写卡）。改为：写卡前检查上位机命令中的显式授权标志位（与上位机约定一个 bit，如 cmd_buf 某保留字段），未置位则**只提示不写卡**（等效 blnBlock=0xff 路径）。
- 真黑名单的处置方式与后台确认：若业务上现场写卡锁定非必需，进站调用直接改 `0xff`，锁卡动作从 TP 中整体退出。
- 无论是否写卡，静默锁卡分支（:6546-6634）全链路输出日志：命中名单条目、命中机制（单卡/区段/越界）、卡号 logicID、cardStatusCode、是否写卡、写卡结果。目标：任何一张被锁卡都能从日志回放事件。

**7.2.3 defer TIMES 分支处置（#5）**
- [:6427-6428](../3018-3030-TP/xa_cpu20_operation.c#L6427) 写卡成功后补 `return`（成功回执路径），消除 fall-through 进 PERIOD 分支；或整体删除 :6419-6428 的改写，TIMES 延期只做回执——改卡统一由后台下发正确值驱动（与 7.2.4 同一模式）。

**7.2.4 0715 修复块移出只读路径（#6、#7）**
- 删除/注释 [CPU_GetFiles1d :962-987](../3018-3030-TP/xa_cpu20_operation.c#L962) 的写卡块。该函数是纯读路径，写卡违反分层且先于交易校验。
- 改为「检测+上报」：若检测到 `activated==1 && time_bcd < start`（疑似改坏），置标志并经 inquire/日志上报（out_buf 标志位或专用返回码），不写卡。
- 修复动作由后台驱动：后台按发卡记录下发完整正确的 1D 记录（含重算后的校验和），经专用修复命令写回。写卡路径统一走 `xa_update_file_1d`（MAC 保护保留），失败仅记录、不拒交易。

**7.2.5 版本号与关键路径日志（#12）**
- main.c 版本号 bump（如 `2026.08.25 止血版`），inquire 回执或日志头打印版本号——终结「版本号未变更、现场无法定位老固件」问题。
- 统一日志宏覆盖所有写卡点：文件 15/17/1C/1D 写、黑名单命中、拒绝码、0715 检测。

### 7.3 P1 巩固

**7.3.1 :6013/:6087 参数 bug（#8）** — `xa_update_file_1c/1d` 改用传入的 `file_buf` 打包（`memcpy(&buf[13], file_buf, len)`），恢复块调用点随即生效；4 处恢复块（:2262-2271 / :2288-2297 / :3429-3466 / :4191-4200）逐一核对回写语义（回写"进交易前的初始值"）。

**7.3.2 基准时间取值点（#9）** — `beforeStartTransTime` 改在主读卡（CPU_GetFiles1d）之前取 `tpCPU.time_bcd`，或在 CPU_GetFiles1d 内先保存原始值再解析，保证恢复基准不被污染。

**7.3.3 激活分支改期（#10）** — 与后台确认"激活时改期"是否仍在产品规格内（发卡系统现在是否直接写正确有效期）。若已废弃，删除改期逻辑；若保留，加票种与值域校验 + 日志。

**7.3.4 校验和统一重算（#11）** — 卡厂商提供 byte15 校验和算法后，在 `xa_update_file_1c/1d/15` 打包 APDU 前统一重算（单一收口点，覆盖所有调用方）。此后任何 TP 改写都可被后台按同算法校验、可回滚。

### 7.4 已坏卡处置

**7.4.1 判别流程（把 6.8.4/6.8.6 实测判别法做成 BOM 页面逻辑）**
1. 查 file 15 cardStatus ≠ 1（实测 04）→ 锁定型；
2. 查 file 1D productStatus ∈ {4,8,9,10}（实测 09）→ 卡内 Applet 已联动锁定；
3. 查 file 17/1A 是否有 transactionType=7 锁卡记录（时间/站点/reasonCode）→ 坐实误锁事件与站点。

**7.4.2 三类坏卡与处置**

| 类型 | 判别特征 | 恢复手段 |
|---|---|---|
| A 锁卡型（03/08 主群体） | cardStatus=04 + productStatus=09 + 文件17 锁卡记录 | 卡厂商解锁命令（若存在）→ 重写 cardStatus=01、productStatus=01 + 校验和 |
| B 有效期改坏型（5.1/5.2 产物） | cardStatus=01、productStatus=01，但起始日期/有效期与发卡记录不符 | 后台按发卡记录下发正确 1C/1D 记录重写（走 7.2.4 修复命令） |
| C 0715 误修型 | validityDurationType=0x03/0x18 且与发卡记录不符 | 同 B，后台下发原始值重写 |

**7.4.3 解锁/恢复工具** — 优先由卡厂商提供解锁命令与校验和算法（同 7.3.4）；若不可得，评估换卡成本。恢复写卡统一走「后台下发正确值」模式，不再由 TP 现场自造。

**7.4.4 存量对账** — 后台用发卡数据对账已报 03/08 的卡，批量生成待恢复清单；试点站先处理 A 型，统计恢复成功率。

### 7.5 后台与卡厂商协同清单

- **1104 名单质量（数据侧根因）**：排序、去重、单卡/区段分开管理、cardStatusCode 语义与业务对齐、区段与发卡号段交叉核对——名单侧不治理，#1/#2/#3 代码修复只挡住一半。
- **卡厂商三件事**：①确认 Applet 对 `0x04D6-0x95` 锁卡写入的联动行为（6.8.3）与 productStatus 码表；②提供解锁/恢复命令；③提供 file 1D/1C byte15 校验和算法。
- **上位机**：进站命令增加「允许写卡锁定」显式位（配合 7.2.2）；故障工单按 7.4.1 三类分流。

### 7.7 实施顺序与风险控制

- **第一批（止血，1 个版本，最高优先级）**：7.2 全部 + 7.6.1/7.6.2 测试 → 试点站灰度 1~2 周 → 全网。风险：改黑名单搜索/删 0715 写卡影响正常功能 → 用 7.6 场景回归兜底。
- **第二批（巩固）**：7.3（:6087 参数 bug、基准时间、激活改期结论、校验和落地后统一重算）。
- **第三批（处置与协同）**：7.4 + 7.5（坏卡批量恢复、BOM 判别功能、名单数据治理、卡厂商解锁命令）。
- 每批独立版本号、独立发布记录；版本号从止血版起强制打印在日志头与 inquire 回执，此后现场分析不再靠二进制比对。

### 7.8 一句话总结

根因不在时钟、不在命令数据，而在固件四处「写卡过于积极」（静默锁卡、defer 改期、0715 只读路径写卡、激活改期）+ 一处「名单误命中放大写卡」+ 一处「兜底空转」；修复顺序是：先止血（P0）、再修兜底（P1）、最后治存量与数据。所有 TP 侧写卡统一收敛为「后台下发正确值 + 校验和 + 日志」三要素。
